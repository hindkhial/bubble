## node-forge 1.4.0 — High, unresolved release blocker

- [GHSA-86w9-cpqp-85rv / CVE-2026-85393](https://github.com/advisories/GHSA-86w9-cpqp-85rv): affected **<=1.4.0**, no patched release listed. The installed version remains affected. RSA PKCS#1 v1.5 nested DigestAlgorithm validation can permit signature forgery with low-exponent keys.
- Audit chain: Bubble → expo → @expo/cli → node-forge. CLI also uses @expo/code-signing-certificates 0.0.6, whose installed `build/main.js` calls `certificate.verify(certificate)` at line 176, `certificate.publicKey.verify(...)` at 203 and CSR verification at 246. CLI `build/src/utils/codesigning.js` calls certificate validation around line 308 when loading configured project signing material.
- This is development/build tooling and is installed in CI/build images. Bubble's app.json has no updates.codeSigningCertificate configuration; the configured web build does not enable that signing workflow. This is static call/configuration evidence, not an exhaustive dynamic proof of every Expo branch. Attacker-controlled signing certificates/keys introduced through tooling are a remaining surface. Do not use this version to validate untrusted signing material.
- Bubble's Java authentication/API and the staging TLS chain use different implementations. No Forge source was present in the inspected 850-entry production web source map. It is not shown to execute in the shipped browser runtime, and builder node_modules are not copied into Nginx. Nevertheless tooling runs before artifacts are emitted: a compromised validation decision could affect artifact integrity in a signing workflow. Runtime image scans do not resolve this build-chain risk.
- No safe published version override exists. Downgrading remains within the affected range. Replacing Forge with Node crypto requires an upstream-compatible certificate-tooling change and independent cryptographic review; it is not a drop-in package alias. Do not apply an unreviewed crypto patch or suppress this finding. Recheck an official fix and rerun exports/certificate-tooling tests before closing; otherwise require explicit security review/acceptance. **Not accepted here.**

## braces 3.0.3 — High, unresolved release blocker

- [GHSA-vfj7-8cjw-p6xm / CVE-2026-93687](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm): affected **<=3.0.3**, no patched release listed. Recursive AST walking on deeply nested patterns can terminate a Node process through stack exhaustion.
- Audit chain: Bubble → expo → @expo/cli → @expo/metro-file-map → micromatch 4.0.8 → braces 3.0.3. Installed micromatch `index.js` calls braces from `.parse` (424–430), `.braces` (451–456) and `.braceExpand` (463–465). Its ordinary matcher uses picomatch (49, 109, 128).
- Metro watcher `build/watchers/common.js` calls `micromatch.some(relativePath, '**/*')` at 31 and configured globs at 33. These are matching calls, not evidence that brace AST expansion is reached. No note, checklist or search input was found passed to braces by Bubble. The package still exists in the development/build/CI graph; this static review cannot certify all possible tool/plugin/config inputs. Restrict build inputs to reviewed repository configuration and never expose a pattern-expansion service.
- No braces or micromatch source appeared in the inspected web map. Runtime denial of service through normal note/search input is not demonstrated. Malicious build configuration invoking an affected expansion API could disrupt artifact generation/CI; availability and build reliability remain relevant even without shipped code. CI has no deployment secrets and runs with read-only repository permissions, but that does not fix recursion.
- No safe published update exists. Picomatch is not an API-equivalent replacement for every braces expansion operation, so an alias/forced removal would risk breaking Metro. Wait for a supported upstream fix or separately review a bounded replacement through its actual consumers. Keep **High/blocking**, without an audit exclusion or speculative severity downgrade.

## uuid 7.0.3 — Moderate, retained with reachability limits

- [GHSA-w5hq-g745-h8pq / CVE-2026-41907](https://github.com/advisories/GHSA-w5hq-g745-h8pq): affected **<11.1.1**, **>=12.0.0 <12.0.1**, **>=13.0.0 <13.0.1**. Listed patched releases are **11.1.1, 12.0.1, 13.0.1**. Do not interpret “11.1.1 or newer” as excluding the later affected releases.
- Audit chain: Bubble → expo → @expo/config-plugins → xcode 3.0.1 → uuid 7.0.3. Installed xcode `lib/pbxProject.js` requires uuid at 22 and generates identifiers with `uuid.v4()` at 90, without a caller-provided output buffer. The vulnerable methods are v3/v5/v6 with insufficient buffer bounds, not this observed v4 call. Package-version applicability remains; exploit reachability through this consumer is not demonstrated.
- This consumer is native project-generation tooling, installed in CI/build dependency graphs. There is no observed affected call in the web build. Installed uuid@7 is absent from the inspected web map. Expo modules-core has separately vendored UUID sources: those must be assessed separately, not declared clean by absence of uuid@7. Malformed native project identifiers could affect generated artifacts if an affected API were introduced later; the observed call has no such input path.
- An official fix exists, but updating 7 → 11 is a multi-major transitive change outside xcode's declared version contract. No stable updated xcode consumer is published in the checked registry. A scoped override could be evaluated separately with native project generation/build tests and API/engine review; a successful require/v4 smoke test alone is insufficient. Retain the visible Moderate finding rather than forcing an unverified replacement during this assessment. Reassess if consumers or exposed buffer APIs change.
